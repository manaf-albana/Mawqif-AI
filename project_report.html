1. ملخص تنفيذي (Executive Summary)

يُقدّم هذا التقرير التوثيق النهائي والهندسي لنظام متكامل يدمج بين الرؤية الحاسوبية على الحافة (Edge AI / Computer Vision) وتقنيات إنترنت الأشياء (IoT) لمراقبة وإدارة مواقف السيارات في الوقت الفعلي. يعمل النظام من خلال مسار مزدوج: 1. المسار الفيزيائي المحلي (Local Edge Loop): كاميرا تلتقط المشهد، ونموذج ذكاء اصطناعي خفيف ومُحسّن (YOLOv8n-cls) يصنّف حالة كل موقف في أجزاء من الثانية (<200ms)، ويرسل الحالة رقمياً عبر اتصال تسلسلي (UART Serial @ 115200 baud) إلى متحكم ESP32 للتحكم الفوري في بوابات الدخول ومؤشرات الإضاءة (LEDs). 2. المسار السحابي والموثوقية (Cloud Telemetry & Resilience Loop): إرسال دوري ومؤمّن عبر بروتوكول HTTPS المشفر بـ TLS 1.2/1.3 إلى منصة ThingSpeak IoT Cloud، مدعوماً بآلية تخزين مؤقت محلي (Local SQLite Store-and-Forward Cache) لحماية البيانات من الضياع عند انقطاع الإنترنت، مع إعادة الإرسال التلقائي للبيانات المعلّقة عند استعادة الاتصال.

5. الجانب الأمني والحماية (20%)

5.1 تشفير طبقة النقل (Transport Layer Security - TLS 1.2/1.3)

تتم كافة عمليات الاتصال الصادرة إلى منصة ThingSpeak عبر بروتوكول HTTPS المنفذ 443 حصراً: * في جانب بايثون (cloud_uploader.py): python resp = requests.post(THINGSPEAK_WRITE_URL, params=payload, timeout=10, verify=True) حيث تفرض خاصية verify=True التحقق الإلزامي من صحة شهادة SSL الموقعة رسمياً من MathWorks، مما يمنع هجمات انتحال الخادم أو التنصت (Man-in-the-Middle Attacks). * في جانب المتحكم ESP32 (main_wifi.ino): يتم استخدام كائن WiFiClientSecure المخصص للاتصالات المشفرة عبر المنفذ 443.

5.2 إدارة الصلاحيات ومبدأ الامتيازات الأقل (Separation of Duties & Least Privilege)

تطبيق فصل صارم بين المفاتيح لمنع التلاعب بالبيانات: 1. مفتاح الكتابة (Write API Key: YOUR_WRITE_API_KEY): - صلاحية مقصورة على دفع وتحديث القراءات فقط. - محمي داخل ملف البيئة المحلي .env وsecrets.h ولا يُمنح إلا للمتحكم والخادم المصرح لهما بالبث. 2. مفتاح القراءة (Read API Key: YOUR_READ_API_KEY): - صلاحية قراءة واستعلام فقط (Read-Only). - يُستخدم لعمليات التحليل الإحصائي، وتوليد التقارير، والعرض في لجان التقييم، دون أي قدرة على تعديل أو حذف البيانات.

5.3 عزل الأسرار البرمجية وتفادي التسريب (Zero Secret Leakage)

  • تم عزل بيانات الاتصال والشبكة بالكامل في ملف .env.
  • تم إعداد ملف .gitignore لحظر رفع ملفات .env، وقواعد البيانات .db، ونماذج الذكاء الاصطناعي على منصات مشاركة الأكواد العامة مثل GitHub.

تم تضمين بروتوكول ArduinoOTA في كود المتحكم main_wifi/main_wifi.ino:

6. الاستمرارية، الموثوقية، وإدارة الطاقة (20%)

6.1 حلول انقطاع الإنترنت (Offline Resilient Store-and-Forward)

لمواجهة احتمالية انقطاع الشبكة في بيئات المواقف الواقعية، يطبق النظام استراتيجية التخزين المؤقت المحلي وإعادة الإرسال: 1. قاعدة البيانات المحلية: محرك SQLite 3 بملف parking_data.db مفعل بنمط WAL (Write-Ahead Logging) لتحقيق سرعة كتابة متزامنة عالية ومقاومة تلف البيانات. 2. مخطط الجدول: sql CREATE TABLE readings ( id INTEGER PRIMARY KEY AUTOINCREMENT, timestamp TEXT NOT NULL, spot1 INTEGER NOT NULL, spot2 INTEGER NOT NULL, spot3 INTEGER NOT NULL, spot4 INTEGER NOT NULL, occupied INTEGER NOT NULL, occupancy REAL NOT NULL, synced INTEGER NOT NULL DEFAULT 0, created_at TEXT DEFAULT (datetime('now', 'localtime')) ); 3. منطق المزامنة الدقيق: - عند محاولة الإرسال السحابي، يتم حفظ السجل مبدئياً كـ synced = 0. - وفقط بعد استلام كود النجاح HTTP 200 مع معرف الإدخال السحابي الصحيح entry_id > 0 من منصة ThingSpeak، يتم تحديث حالة السجل إلى synced = 1. - في حال حدوث انقطاع (Socket Error أو Connection Timeout)، يظل السجل في قائمة الانتظار synced = 0.

6.2 نتائج الاختبار التجريبي لإعادة الإرسال (Verified Resilience Test)

تم إجراء اختبار ميداني خاضع للرقابة لمحاكاة انقطاع الإنترنت ثم استعادته، وجاءت النتائج الفيزيائية كما يلي: * إجمالي القراءات المسجلة محلياً في قاعدة البيانات: 1,715 سجلاً (حجم الملف: 144 KB). * اختبار إعادة الإرسال الدفعي: بعد استعادة الاتصال بالإنترنت، قام النظام باسترجاع دفعة تجريبية مكونة من 20 سجلاً تاريخياً معلّقاً من جدول readings (من السجل رقم 2 وحتى السجل 21)، وتولى محرك المزامنة إرسالها تباعاً إلى المنصة السحابية مع احترام الفاصل الزمني الإلزامي لـ ThingSpeak (15 ثانية بين كل طلب)، وتأكيد نجاح المزامنة بنسبة 100% (20/20) وتحديث حالتها في قاعدة البيانات إلى synced = 1. * السجلات المتبقية في المخزن المؤقت: بقيت السجلات الـ 1,694 الأخرى بحالتها الموثقة بدقة كـ synced = 0 داخل المخزن المحلي، مما يضمن أمانة التوثيق ويوفر دليلاً عملياً وقاطعاً على جاهزية آلية الـ Resend دون تزوير أو تضخيم غير واقعي لأرقام السحابة.

6.3 إدارة استهلاك الطاقة (Power Management)

تم تطبيق حلول متقدمة لترشيد الطاقة على مستوى العتاد والبرمجيات: 1. تفعيل نمط Modem-Sleep للواي فاي: تم تضمين الأمر الصريح WiFi.setSleep(true); في كود المتحكم main_wifi.ino. يعمل هذا النمط على إيقاف تشغيل دارة الراديو (RF Synthesizer & Power Amplifier) أثناء فترات عدم نقل البيانات، مما يقلل متوسط سحب التيار من ~120-140mA إلى ~20-30mA فقط (توفير يتجاوز 75% من الطاقة). 2. جدولة الإرسال بنسبة تشغيل منخفضة (Radio Duty-Cycling): بدلاً من الإرسال المستمر مع كل إطار فيديو (30 مرة بالثانية)، يلتزم النظام بدورة إرسال كل 15 ثانية (CLOUD_INTERVAL_MS = 15000). يستغرق بث الحزمة السحابية الواحدة عبر HTTPS قرابة 250ms، ما يعني أن دورة تشغيل الراديو اللاسلكي الفعلي لا تتجاوز: $$\text{Duty Cycle} = \frac{250\text{ ms}}{15000\text{ ms}} \approx 1.66\%$$ بينما يبقى الراديو في وضع الخمول المنخفض طوال 98.34% من الوقت. 3. توزيع الأحمال الحسابية (Edge Offloading Architecture): تتم معالجة الشبكات العصبية العميقة كثيفة الاستهلاك (YOLO Inference) على الحاسب المضيف (Edge Host)، بينما يتفرغ معالج ESP32 للمهام الخفيفة وإدارة الإشارات والمؤشرات، مما يمنع ارتفاع حرارة المتحكم ويطيل عمره الافتراضي ويجعل تشغيله عبر بطارية صغيرة أمراً ممكناً هندسياً. 4. تأخير الخمول التكيفي لـ FreeRTOS: إدراج أمر delay(10); ضمن حلقة loop() الرئيسية يتيح لمجدول نظام التشغيل اللحظي (FreeRTOS) تشغيل مهمة الخمول (Idle Task)، مما يضع أنوية المعالج (Xtensa Dual-Core) في حالة السكون المؤقت عند غياب أي دخل عبر المنفذ التسلسلي.

8.2 كود التحليل الرياضي بلغة MATLAB (ThingSpeak MATLAB Analysis)

تم إعداد وتطبيق كود التحليل الإحصائي المتقدم داخل بيئة ThingSpeak السحابية لحساب الاتجاهات وكشف القيم الشاذة المتطرفة:

% =====================================================
% Smart Parking Analytics Engine — MATLAB Script
% Channel ID: 3518913
% =====================================================

channelID = 3518913;
readKey   = 'YOUR_READ_API_KEY';

% قراءة البيانات التاريخية
[data, time] = thingSpeakRead(channelID, 'Fields', [5, 6], 'NumPoints', 50, 'ReadKey', readKey);
occupiedCount = data(:, 1);
occupancyRate = data(:, 2);

% 1. حساب المتوسطات والانحراف المعياري
meanRate = mean(occupancyRate, 'omitnan');
stdRate  = std(occupancyRate, 'omitnan');

% 2. كشف القيم المتطرفة والشاذة (Anomaly Detection: 2-Sigma Rule)
upperThreshold = meanRate + (2 * stdRate);
anomalies = find(occupancyRate > upperThreshold);

% 3. تحليل ميل الاتجاه الزمني (Linear Trend Slope)
x = (1:length(occupancyRate))';
p = polyfit(x, occupancyRate, 1);
slope = p(1);

fprintf('--- نتائج التحليل الإحصائي لمواقف السيارات ---\n');
fprintf('متوسط نسبة الإشغال: %.2f%%\n', meanRate);
fprintf('الانحراف المعياري: %.2f%%\n', stdRate);
fprintf('عدد حالات الازدحام الشاذة: %d حالة\n', length(anomalies));
if slope > 0.05
    fprintf('اتجاه الحركة: تصاعدي (ازدياد تدفق السيارات)\n');
elseif slope < -0.05
    fprintf('اتجاه الحركة: تنازلي (مغادرة السيارات للمواقف)\n');
else
    fprintf('اتجاه الحركة: حالة استقرار عام\n');
end

10. الخلاصة واستعداد المناقشة الشفهية

أثبتت النتائج الهندسية للمشروع عمل كافة مكونات النظام بتناغم وموثوقية عالية: 1. الرؤية الحاسوبية: سرعة فائقة في رصد المواقف وعكسها فيزيائياً وسحابياً. 2. الأمان الميداني: اتصالات مشفرة بـ TLS ومفاتيح API معزولة وتحديث لاسلكي آمن (OTA). 3. الاستمرارية الهندسية: مرونة تامة في التعامل مع سيناريوهات انقطاع الاتصال بفضل تقنية الـ SQLite Caching المجرّبة ميدانياً. 4. التحليل الرقمي: لوحة تحكم تفاعلية عامة متاحة لتقييم لجنة المناقشة تقدم رسوماً حية وتحليلاً إحصائياً واضحاً للاتجاهات.
